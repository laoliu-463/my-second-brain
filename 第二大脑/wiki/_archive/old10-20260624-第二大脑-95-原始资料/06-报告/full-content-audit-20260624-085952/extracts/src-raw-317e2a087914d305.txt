下面是**可直接复制给编码 Agent / Harness 执行的完整 DDD 重构提示词包**。每个编号都是**一次独立任务**，不要合并执行。整体原则是：**先审查和补测试，再加门面，再抽策略，再替换调用，最后清理旧依赖**。

依据知识库边界：用户域统一提供身份、角色、人员主数据和数据范围解析；订单域只同步、存储、默认归因，不计算提成、不应用独家规则；业绩域负责最终归属、提成、毛利和独家商家；商品域负责活动、合作方、活动商品关联、展示规则、转链与快速寄样入口；寄样域负责申请、审核、发货、完成、拒绝、关闭；配置域负责系统参数和配置更新事件；分析模块只消费事件维护汇总表，不重算业务归属。

# 一、总控提示词

这个提示词放在每次任务最前面，作为执行 Agent 的通用规则。

```text
你现在在 D:/Projects/SAAS 团长 SaaS 项目中执行 DDD 代码重构任务。

【项目背景】
当前项目已经完成 DDD 知识库全盘梳理。后续要按用户域、配置域、商品域、达人域、寄样域、订单域、业绩域、分析模块逐步重构代码。当前系统已经能运行，真实联调环境和业务流程不能被破坏。

【核心目标】
用小步、安全、可回滚的方式进行 DDD 重构：
1. 先补防护测试，再改生产代码。
2. 先新增 Facade / Port / Policy / ApplicationService，再逐步迁移旧逻辑。
3. 先保持旧接口、旧响应、旧数据库行为不变，再内部替换实现。
4. 每次只做一个任务，不允许跨任务顺手重构。
5. 每次任务必须独立提交、独立报告、独立验证。

【当前技术栈约束】
以当前仓库实际代码为准。若知识库早期文档出现 FastAPI / Celery 等旧技术描述，不要照搬技术栈；当前项目实际以后端 Spring Boot、前端 Vue3、PostgreSQL、Redis、Docker Compose、harness 脚本为准。具体命令必须先查看仓库 README、harness 文档、package/maven 配置后再执行。

【领域边界硬规则】
1. 用户域：
   - 负责身份、角色、权限、组织架构、人员主数据、数据范围解析。
   - 其他业务域不得新增 SysUserMapper 直接注入。
   - 业务域只能通过 UserDomainFacade 获取 data_scope、渠道列表、招商列表、组员列表、操作权限。
2. 配置域：
   - 负责系统参数、提成比例、寄样限制、独家阈值、保护期、复制模板。
   - 其他业务域不得直接查 system_config Mapper。
   - 业务域只能通过 ConfigDomainFacade 读取配置。
3. 商品域：
   - 负责活动、合作方、商品、活动商品关联、商品库展示、置顶、转链、快速寄样入口。
   - 不负责订单归属计算，不负责寄样流程，不负责达人归属。
4. 达人域：
   - 负责达人基础信息、多人认领、保护期、标签、地址、独家达人资格。
   - 不负责寄样申请流程，不负责订单业绩计算。
5. 寄样域：
   - 负责申请、审核、发货、签收、待交作业、完成、拒绝、关闭。
   - 不直接管理商品详情、达人详情、订单归属、提成计算。
6. 订单域：
   - 只同步、存储、更新订单事实。
   - 只存默认归因：pick_source 默认渠道、activity/product 默认招商。
   - 不计算服务费收益、招商提成、渠道提成、毛利。
   - 不应用独家达人、独家商家规则。
7. 业绩域：
   - 负责最终渠道、最终招商、独家覆盖、服务费收益、招商提成、渠道提成、毛利。
   - 对预估轨和结算轨分别计算。
   - 提成比例只读配置域。
8. 分析模块：
   - 只消费事件维护汇总表。
   - 不重新计算最终归属。
   - 不修改业务域数据。

【安全红线】
1. 禁止修改公网 API 路径、入参、出参，除非任务明确要求。
2. 禁止删除旧 Service、旧 Mapper、旧接口，除非任务明确进入 CLEAN 阶段。
3. 禁止破坏性 migration：禁止 drop / rename / 清表。
4. migration 只能新增表、新增 nullable 字段、新增索引、新增兼容约束。
5. 禁止 real-pre 执行破坏性 SQL。
6. 禁止一次性大规模改包名、搬目录、重命名类。
7. 禁止把多个任务合并成一个 commit。
8. 禁止引入 Kafka/RabbitMQ 等新外部依赖，除非任务明确要求。
9. 禁止让事件失败影响订单落库、寄样申请、配置保存等核心流程，除非旧逻辑原本如此且有测试证明。
10. 禁止“感觉没问题就结束”，必须跑测试、生成报告、说明风险。

【每个任务开始前必须做】
1. git status，确认当前工作区状态。
2. 阅读本任务涉及的领域文档。
3. 搜索当前代码实现，列出会修改的文件。
4. 判断是否需要新增测试；除纯文档任务外，必须新增或更新测试。
5. 写出本任务最小改动方案。
6. 明确不做的内容。

【每个任务完成后必须做】
1. git diff --stat
2. git diff 核查是否有无关修改。
3. 运行 targeted tests。
4. 运行后端全量测试。
5. 涉及前端时运行前端 targeted tests 和 build。
6. 涉及数据库时验证 migration 可重复、可回滚或向后兼容。
7. 涉及金额时做 API/DB/汇总对账。
8. 涉及权限时做 admin、组长、普通成员三角色对账。
9. 涉及事件时做幂等测试。
10. 生成 harness/reports/<task-id>-<date>.md。
11. 单独 commit，commit message 必须包含任务编号。
12. 最终输出：修改摘要、测试结果、风险、回滚方案、提交号。

【输出格式】
请按以下格式输出：
1. 任务理解
2. 当前代码定位
3. 修改计划
4. 实际修改
5. 测试结果
6. 影响范围
7. 风险与回滚
8. 生成的报告路径
9. commit hash
10. 下一步建议

现在开始执行我随后给你的具体任务。
```

# 二、Phase 0：重构准入与防护基线

## DDD-BASE-001：新增 DDD 重构安全开关

```text
你现在执行 DDD-BASE-001：新增 DDD 重构安全开关。

【目标】
建立后续 DDD 重构的统一安全开关，默认全部关闭，不改变任何当前业务行为。

【必须新增的配置项】
请在当前项目配置体系中新增以下配置，默认全部 false：
1. ddd.refactor.enabled
2. ddd.refactor.user-facade.enabled
3. ddd.refactor.config-facade.enabled
4. ddd.refactor.product-facade.enabled
5. ddd.refactor.talent-facade.enabled
6. ddd.refactor.sample-application.enabled
7. ddd.refactor.order-application.enabled
8. ddd.refactor.order-attribution.enabled
9. ddd.refactor.order-amount-policy.enabled
10. ddd.refactor.performance-calc.enabled
11. ddd.refactor.performance-query.enabled
12. ddd.refactor.analytics-shadow.enabled
13. ddd.refactor.outbox.enabled

【执行步骤】
1. git status，确认工作区。
2. 搜索项目当前配置读取方式，包括 application.yml、application-real-pre.yml、application-test.yml、配置属性类。
3. 新增配置属性类，例如 DddRefactorProperties，字段与上述开关对应。
4. 确保所有开关默认 false。
5. 不让任何业务代码读取这些开关改变行为，本任务只建立配置。
6. 新增单元测试：
   - 默认配置加载时所有开关为 false。
   - 显式设置 true 时可正确读取。
7. 新增报告：
   - harness/reports/ddd-base-001-refactor-switches.md
   - 内容包括开关列表、默认值、用途、回滚策略。
8. 运行 targeted test。
9. 运行后端全量测试。
10. git diff 核查无业务路径改动。
11. 单独 commit：DDD-BASE-001 add DDD refactor safety switches。

【禁止】
1. 禁止修改任何 Controller。
2. 禁止修改任何 Service 业务路径。
3. 禁止修改数据库。
4. 禁止开启任何重构开关。

【验收标准】
1. 所有开关默认 false。
2. 测试通过。
3. 当前接口行为完全不变。
```

```text

【执行步骤】

11. 运行后端全量测试。
12. 若涉及前端页面快照，运行前端 targeted tests。
13. 单独 commit：DDD-BASE-002 add characterization tests。

【禁止】
1. 禁止修改生产代码。
2. 禁止修改数据库结构。
3. 禁止为了让测试通过而改业务逻辑。
4. 禁止接真实外部 API。

【验收标准】
1. 新增测试全部通过。
2. 当前行为被清晰冻结。
3. 报告说明后续重构可依赖的基线。
```

## DDD-BASE-003：跨域依赖扫描与 ArchUnit 防回退

```text
【验收标准】
1. 依赖地图完整。
2. 有防止新增跨域 Mapper 的测试。
```

# 三、Phase 1：用户域统一数据范围

用户域是全系统数据范围和人员主数据入口，业务域要接收用户域解析后的 self/group/all，而不是自己重复实现。用户域文档明确提供渠道/招商/部门/组员和 data_scope 能力。

## DDD-USER-001：新增 UserDomainFacade

```text
你现在执行 DDD-USER-001：新增 UserDomainFacade。

【目标】
建立用户域对其他领域的唯一只读门面。当前先委派旧 SysUserService / SysUserMapper，不改变任何业务结果。

【新增能力】
新增 UserDomainFacade，至少包含：
1. resolveDataScope(Long userId)
2. checkPermission(Long userId, String resource, String action)
3. listChannels(String keyword)
4. listRecruiters(String keyword)
5. listDepartments()
6. listGroupMembers(Long groupId)
7. getUserBrief(Long userId)
8. batchGetUserBrief(Collection<Long> userIds)

【DTO 要求】
1. DataScopeDTO：
   - scopeType: all/self/group/custom
   - userIds
   - channelIds
   - recruiterIds
   - departmentIds
   - isAll()
2. UserBriefDTO：
   - userId
   - username
   - realName
   - roleCodes
   - groupId
   - departmentId
   - status

【执行步骤】
1. git status。
2. 搜索当前用户服务和 Mapper。
3. 新增 UserDomainFacade 接口。
4. 新增 LegacyUserDomainFacade 实现，内部委派旧逻辑。
5. 不替换任何业务域调用。
6. 新增测试：
   - admin -> all
   - recruiter_lead -> group
   - recruiter -> self
   - channel_lead -> group
   - channel -> self
   - disabled user 的处理保持旧行为。
7. 对 listChannels/listRecruiters 做字段和数量断言。
8. 运行用户域 targeted tests。
9. 运行后端全量测试。
10. 更新 dependency map，标记 UserDomainFacade 是后续替换入口。
11. 生成报告：
   - harness/reports/ddd-user-001-user-domain-facade.md
12. 单独 commit：DDD-USER-001 add UserDomainFacade。

【禁止】
1. 禁止替换订单、寄样、业绩调用。
2. 禁止修改权限规则。
3. 禁止删除 SysUserService。
4. 禁止改变前端用户接口响应。

【验收标准】
1. Facade 可用。
2. 默认行为不变。
3. 测试覆盖所有角色数据范围。
```

## DDD-USER-002：订单域数据范围改走 UserDomainFacade

```text
你现在执行 DDD-USER-002：订单域数据范围改走 UserDomainFacade。

【目标】
订单列表、订单详情、订单导出、筛选下拉不再新增直接依赖 SysUserMapper。先保留旧 fallback，默认结果必须与旧逻辑一致。

【改造范围】
1. 订单列表数据范围过滤。
2. 订单详情权限校验。
3. 订单导出权限和过滤。
4. 渠道下拉。
5. 招商下拉。
6. 部门下拉。

【执行步骤】
1. git status。
2. 搜索订单域里 SysUserMapper、SysUserService、DataScopeAspect、applyDataScopeFilter 的使用点。
3. 为订单域新增 OrderDataScopeAdapter 或直接注入 UserDomainFacade。
4. 保持 SQL 过滤字段不变：
   - 渠道维度使用 default_channel_id 或 final_channel_id，以当前代码实际为准。
   - 招商维度使用 default_recruiter_id 或 final_recruiter_id，以当前代码实际为准。
5. 新路径和旧路径结果必须一致。
6. 保留 fallback：
   - ddd.refactor.user-facade.enabled=false 时旧路径。
   - true 时新路径。
```

## DDD-PERF-002：抽取 PerformanceMoneyPolicy

```text
你现在执行 DDD-PERF-002：抽取 PerformanceMoneyPolicy。

【目标】
把预估轨和结算轨的服务费收益、招商提成、渠道提成、毛利计算集中到一个纯 Policy。

【公式】
对 track in {estimate, effective} 分别计算：
1. 服务费收入(track) = 订单对应服务费字段。
2. 技术服务费(track) = 订单对应技术服务费字段。
3. 服务费收益(track) = 服务费收入(track) - 技术服务费(track)。
4. 招商提成(track) = 服务费收益(track) * 招商提成比例。
5. 渠道提成(track) = 服务费收益(track) * 渠道提成比例。
6. 毛利(track) = 服务费收益(track) - 招商提成(track) - 渠道提成(track)。

【退款/失效规则】
1. 已退款：is_valid=false，提成和毛利归零，is_reversed=true。
2. 已失效：is_valid=false，不计入汇总。
3. 待结算：预估轨可有值，结算轨通常为0。
4. 已结算：预估轨和结算轨都按字段计算。

【执行步骤】
1. git status。
2. 搜索业绩金额计算散落代码。
3. 新增 PerformanceMoneyPolicy。
4. 先写纯单元测试。
5. 将旧业绩计算中的金额公式委派给 Policy。
6. 金额精度和舍入规则保持当前系统一致。
7. 新增测试：
   - 预估轨正常计算。
   - 结算轨正常计算。
   - 结算轨为0时不产生结算提成。
   - 技术服务费扣减正确。
   - 招商提成比例正确。
   - 渠道提成比例正确。
   - 毛利正确。
```
