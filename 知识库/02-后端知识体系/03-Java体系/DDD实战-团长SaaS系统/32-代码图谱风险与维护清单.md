# 代码图谱风险与维护清单

## 概述

本文整理 code-review-graph 暴露的结构风险、维护热点和后续复查问题。这里的“风险”不是缺陷结论，而是图谱信号：连接多、函数长、跨社区耦合强、测试映射不完整或承担桥接职责。是否需要修复，必须再结合业务优先级、当前变更、测试结果和线上证据判断。

## 高耦合社区

| 社区关系 | 边数 | 图谱含义 | 维护建议 |
| --- | ---: | --- | --- |
| `e2e-api` → `helpers-assert` | 415 | E2E 与 helper / 断言高度耦合 | helper 改动必须跑相关 E2E，避免多个脚本同时失效 |
| `api-it:calls` → `product-handle` | 173 | 前端 API 层与商品/订单等视图强耦合 | API 字段变更必须同步视图、Vitest 和 E2E |
| `utils-error` → `product-handle` | 118 | 统一错误提示被多个视图依赖 | 401/403/业务错误提示改动影响面大 |
| `e2e-api` → `router-redirect` | 18 | E2E 与路由/重定向相关 | 登录、菜单、跳转规则改动要跑角色流 |
| `product-handle` → `constants-attribution` | 13 | 订单归因展示文案跨页面复用 | 前端不得自行定义和后端不一致的归因原因 |

## 桥接节点

| 节点 | 图谱信号 | 说明 |
| --- | --- | --- |
| `11-real-pre-role-business-flow.spec.ts` | bridge 最高，degree 467 | 角色菜单、权限、业务交接综合脚本 |
| `33-real-pre-sample-chain.spec.ts` | bridge 高 | 寄样链 real-pre 验收脚本 |
| `36-real-pre-cleanup-plan.spec.ts` | bridge | 清理计划和部署后收口脚本 |
| `12-real-pre-full-business-journey.visual.spec.ts` | bridge | 多角色可视化旅程 |
| `23-v1-rbac-scope.spec.ts` | 多个权限 bridge 节点 | 401/403、角色访问、数据范围验证 |

桥接测试是验收网络的一部分，不是普通工具函数。维护原则是：先保证证据清晰和失败可定位，再考虑重构。

## 图谱提示的知识缺口

| 类型 | 图谱发现 | 解释 |
| --- | --- | --- |
| `isolated_nodes` | SQL 表节点、测试内部类、简单 helper 等大量 degree=1 节点 | 多数是图谱解析粒度问题，不必全部修 |
| `thin_communities` | `backend`、`composables-use`、`config-product` 等小社区 | 可能是独立小文件，也可能是聚类边界过细 |
| `single_file_communities` | `vite.config.ts`、`ProductSelectionCard.vue` 等 | 单文件社区不必强行合并，但应避免孤立业务逻辑 |
| `untested_hotspots` | `ProductService`、`toActivityProductView`、`getOrderDetail` 等 | 不能直接等同“没有测试”，但应在改动时主动查测试覆盖和 E2E |

## 需要复查的问题

| 优先级 | 问题 | 需要的证据 |
| --- | --- | --- |
| 高 | real-pre 角色业务流脚本是否有清晰文档和失败定位？ | `tests/e2e/11-real-pre-role-business-flow.spec.ts`、`docs/验收/` |
| 高 | real-pre 寄样链脚本是否能明确区分环境阻塞、数据缺失和功能失败？ | `tests/e2e/33-real-pre-sample-chain.spec.ts`、real-pre 日志、SQL/API |
| 中 | `ProductService.generatePromotionLinkInternal` 修改是否覆盖转链、mapping、真实写开关和 fallback？ | 单测、E2E、`pick_source_mapping` SQL |
| 中 | `AttributionService.resolveAttribution` 的规则优先级是否仍与业务口径一致？ | 业务 ADR、单测、真实订单样本 |
| 中 | 前端 `utils/requestError.ts` 改动是否会影响商品、订单、数据、抖音联调页？ | Vitest、Playwright、手动页面截图 |
| 中 | `DataApplicationService` 的统计口径是否与 Dashboard / 导出一致？ | Dashboard 对账、订单导出对比 |
| 低 | 小社区和单文件社区是否只是聚类结果？ | 文件职责检查，不建议为了图谱好看重构 |

## 不能直接下的结论

- 不能因为 `ProductService` 是热点，就断定它有 bug。
- 不能因为 `tests_for=0`，就断定某类没有任何测试。
- 不能因为 E2E 是 hub / bridge，就认为测试设计错误。
- 不能因为跨社区调用多，就马上要求拆模块。
- 不能用图谱替代真实运行、日志、SQL、接口响应和 E2E 报告。

## 维护建议

1. 改商品、转链、归因、订单、寄样时，先看 [[DDD实战-团长SaaS系统/29-后端代码图谱脉络|后端代码图谱脉络]] 的热点入口。
2. 改页面、接口字段、错误提示、路由菜单时，先看 [[DDD实战-团长SaaS系统/30-前端页面与API图谱脉络|前端页面与API图谱脉络]]。
3. 改验收脚本、real-pre、P0、角色流时，先看 [[DDD实战-团长SaaS系统/31-测试验收与QA图谱脉络|测试验收与QA图谱脉络]]。
4. 每次重大变更后重新跑 `build_or_update_graph_tool`，再更新本系列笔记中的图谱快照。
5. 图谱只记录结构事实；最终结论仍按“现象 → 证据 → 推论 → 结论”链路写入对应问题笔记或验收文档。
